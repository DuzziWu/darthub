## Outcome

The 502 was **not** an application fault. It was an operational bind-address
fault, confirmed independently of the DevOps diagnosis.

The live preview had been restarted with the E2E suite's `HOSTNAME=127.0.0.1`
convention, so the host-side proxy could not open a TCP connection to
`172.18.0.2:3000` and answered 502. The application answered 200 to every
request from inside the container — which is precisely why the site looked
broken while every local health check passed.

Two findings that change the fix:

1. **The port collision was the trigger, not an independent mistake.**
   `playwright.config.ts` had its root-build server on port 3000 with
   `reuseExistingServer`, so the E2E run displaced the live preview and took
   the port bound to loopback. That is what replaced the last working
   `0.0.0.0` configuration. Moving the suite off port 3000 is therefore part
   of the fix, not hygiene.
2. **The documentation gap is what allowed the incident.** The application
   side was hardened twice (`ff98d43` introduced the prefix mechanism,
   `07d9e80` added a build-time gate that fails when asset URLs miss the mount
   prefix), while the operational side was only ever _documented_
   (`8b979ad`) and then violated in practice. `HOSTNAME=0.0.0.0` existed only
   in `AGENTS.md` and never in `docs/DEPLOYMENT.md`.

Both commits after `origin/main` were ruled out as causes: `07d9e80` is
build-time only, `eff1313` is purely client-side, and a 502 is a
connection-refused signal that neither can produce. The running binaries
contained both changes and still produced the 502.

The proxy semantics were read from the source, not assumed:
`e2e/subpath-preview.spec.ts:75-78` turns an upstream **connection error** into
502 and pipes a 404/500 response through verbatim. A 502 is therefore always a
reachability signal and never a routing signal. `next.config.ts` uses
`assetPrefix` rather than `basePath` deliberately: `basePath` would move the
routes under the prefix as well, and the proxy strips the prefix before
forwarding, so the backend would answer 404.

## Open issues

Two latent defects, both application-level, neither capable of producing a 502:

1. **Invariant 7 — the current-route marker is lost after client-side
   navigation.** Under the prefix build `usePathname()` returns the _prefixed_
   path, because the router `basePath` is deliberately empty (`assetPrefix` is
   used instead) and `removeBasePath` therefore never fires. After a full page
   load the server-rendered markup still carries the marker; after a
   client-side navigation no entry is marked current. Measured: full load
   `/lobby` → `current = ["/darthub/lobby"]`; client navigation to `/lobby` →
   `current = []`. The root build is unaffected, so the defect exists precisely
   in the production configuration. `e2e/subpath-preview.spec.ts` only
   exercises full loads, which is why the suite is green while the defect is
   live.
2. **Invariant 8 — the prefix gate cannot catch an omission.** The Dockerfile
   never sets `BASE_PATH`, so the image is always a root build and
   `check-asset-prefix.mjs` always passes on it. The gate can detect a
   _mismatch_ but never an _omission_.
