## Known failures (the baseline)

**There are none.** The baseline is green: typecheck, lint, format check and the
full Vitest suite all pass. The repairs that got it there are recorded in
`docs/ai-skills/README.md` §2.4.

Two checks stay conditional, so they do not fail the suite on a machine that
lacks the tooling:

| Test                                            | Skipped when                                 |
| ----------------------------------------------- | -------------------------------------------- |
| `tests/unit/dockerignore.test.ts` (live build)  | `DART_DOCKER_BUILD` is not set               |
| `tests/unit/tailwind/tailwindToolchain.test.ts` | no successful `npm run build` output present |

The live `docker build` in `tests/unit/dockerignore.test.ts` is **opt-in**: it
runs only when `DART_DOCKER_BUILD=1` is set, and the flag is what skips it —
not the state of the machine. Without the flag the default suite run does not
touch the Docker daemon at all (it does not even run `docker info`), the
structural `.dockerignore` checks still run, and the skip is visible: the
reason is printed to stdout (`[dockerignore] DART_DOCKER_BUILD is not set: …`)
and the test title names the flag. With the flag set the build needs a
reachable daemon, and a **missing daemon is a hard failure**, not a skip. Run
it with `DART_DOCKER_BUILD=1 npm test -- tests/unit/dockerignore.test.ts`; CI
does the same in its `Test (Docker image)` step.

`tests/unit/dockerignoreBuild.test.ts` proves the default run starts no
`docker build`: it runs the dockerignore suite in a child process with a
`docker` shim first on `PATH` and asserts that the shim recorded no
invocation.

`tests/unit/ci-workflow.test.ts` guards the CI side: it asserts that a
dedicated step sets `DART_DOCKER_BUILD=1` and runs the dockerignore suite,
that the plain unit-suite step does not set the flag, and that the meta test
does not replay the docker step locally.

Component tests need a per-file `// @vitest-environment jsdom` docblock —
the global environment stays `"node"`. The Testing Library `cleanup()` is
registered globally in `tests/setup.ts`, so no test file needs its own
`afterEach` cleanup, and a React root can no longer outlive the jsdom
environment.

## Writing a new test

1. Mirror the source path under `tests/unit/` or `tests/integration/`.
2. Name the file `*.test.ts` / `*.test.tsx`.
3. Title the test as a descriptive sentence: `it('restores the state before the dart', ...)`.
4. Cover the failure path.
5. For an engine rule, add a correction-replay case.
6. For a `MutableMatchState` fixture, include `throws` and `corrections`.
7. Prefer an in-memory double over real infrastructure.
8. Keep coverage at or above 80 % (`.claude/testing.md`).
