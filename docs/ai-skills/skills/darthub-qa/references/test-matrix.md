## Known failures (the baseline)

**There are none.** The baseline is green: typecheck, lint, format check and the
full Vitest suite all pass. The repairs that got it there are recorded in
`docs/ai-skills/README.md` §2.4.

Two environment-dependent checks stay conditional, so they do not fail the
suite on a machine that lacks the tooling:

| Test                                            | Skipped when                                         |
| ----------------------------------------------- | ---------------------------------------------------- |
| `tests/unit/dockerignore.test.ts`               | no Docker **daemon** reachable (`docker info` fails) |
| `tests/unit/tailwind/tailwindToolchain.test.ts` | no successful `npm run build` output present         |

The `dockerignore` test guards on daemon reachability, not on the presence of
the `docker` CLI: the client can be installed while the daemon is not running,
and the live build needs the daemon.

Component tests need a per-file `// @vitest-environment jsdom` docblock —
the global environment stays `"node"`. The Testing Library `cleanup()` is
registered globally in `tests/setup.ts`, so no test file needs its own
`afterEach` cleanup, and a React root can no longer outlive the jsdom
environment.

## Writing a new test

1. Mirror the source path under `tests/unit/` or `tests/integration/`.
2. Name the file `*.test.ts` / `*.test.tsx`.
3. Title the test as a descriptive sentence: `it('restores the state before the dart', ...)`.
4. Cover the failure path.
5. For an engine rule, add a correction-replay case.
6. For a `MutableMatchState` fixture, include `throws` and `corrections`.
7. Prefer an in-memory double over real infrastructure.
8. Keep coverage at or above 80 % (`.claude/testing.md`).
