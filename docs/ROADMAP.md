## Milestones

1. **M1 Playable Core**: engine with 501 and Cricket, rooms, and two browser clients finishing a match.
2. **M2 Rated Product**: guest and registered flows, ratings persisted and displayed, friends and invites working.
3. **M3 Content and Compliance**: career mode playable, GDPR export and delete verified, Docker deployment on a fresh VPS.
4. **M4 Release Candidate**: E2E suite green, review findings closed, documentation complete.

## Risks and Mitigations

- Guest-to-user migration data loss: transactional migration plus unit tests.
- Cheating in real-time play: server-side validation of every throw and checksums of AI moves.
- Camera SDK variability: all hardware-specific code stays behind one interface.
- Elo calculation load: nightly batch updates and stored procedures if needed.
- GDPR compliance depth: exhaustive export and delete now; external audit later.

## Open Security Work

The hardening stage (branch `fix/security-auth-hardening`) closed the gaps
that the code audit of 2026-11-17 found. These remain open:

| #   | Gap                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Where it lives                                            |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 1   | The rate limiter covers the own sign-in route, the registration, the guest conversion, the invitation flow and the **Auth.js provider callbacks** (credential sign-in and guest session). The friend requests, the privacy export and the Socket.IO events carry no limit.                                                                                                                                                                                                                                                                                                                                                                                | `src/security/`, `src/friends/`, `src/realtime/`          |
| 2   | **The Auth.js callbacks were secured in the hardening stage, and the order matters.** The credential callback and the guest callback are counted in front of Auth.js (`src/auth/authjsRoute.ts`), so the expensive password comparison and the guest session happen only for a request the limit allowed. `AUTH_TRUST_HOST=true` — which the Auth.js path needs in a self-hosted deployment — **must not be set before this protection is in place**, and the new login page must not ship before it either. `AUTH_TRUST_HOST` is a host check, not a rate limit: it says which origins may talk to the application, not how many passwords may be tried. | `src/auth/authjsRoute.ts`, `src/auth/authjsRouteGuard.ts` |
| 3   | The realtime invitation codes are still drawn from `Math.random()` — the auth codes were moved to the cryptographic generator, the realtime module belongs to the realtime vertical.                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | `src/realtime/inviteService.ts`                           |
| 4   | The invitation codes live in the memory of one process: a restart invalidates them, and several instances do not share them.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | `src/auth/invitationStore.ts`                             |
| 5   | The data export carries the profile only; the ratings, the matches, the friendships and the career progress are still empty placeholders.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | `src/privacy/exportService.ts`                            |
| 6   | The audit logger exists but the privacy routes do not call it, and the file it writes to is not part of the container image.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | `src/privacy/auditService.ts`                             |
| 7   | The session tokens are stateless: a stolen token stays valid until it expires, and there is no way to revoke it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | `src/auth/session.ts`                                     |
| 8   | No security headers, no origin check on the write endpoints.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | `next.config.ts`                                          |
| 9   | The guest conversion is not atomic: the account is created first, the migration second.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | `src/auth/linkGuestRoutes.ts`                             |
| 10  | The client address of a request comes from a header the client controls. The hardening stage reads the **last** entry of `x-forwarded-for` — the entry the closest proxy added — and binds the published port of the application to the loopback address of the host. The application must nevertheless only be reachable through a proxy that sets the address correctly; the per-account limit is the limit that holds either way.                                                                                                                                                                                                                      | `src/security/clientAddress.ts`, `docker-compose.yml`     |
