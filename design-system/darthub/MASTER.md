# PART II — DARTHUB DECISIONS (overriding the persisted base)

## 2. Direction

**"The board, after dark."** A warm-black instrument surface where the board's own colours carry game meaning, the score is a ruled sheet read at a glance, and the only warm thing on screen is the lit board.

Full comparison and rejection reasoning: `reports/design/02-direction-decision.md`.

### 2.2 Where the DartHub palette comes from

Not from the dataset — the dataset has no darts palette (`--domain color "darts"` returns nothing usable; the two profiles it does have, "Gaming" neon purple/rose and "Sports Team/Club" red on light pink, are both rejected as decoration). The palette is derived from **dartboard semantics**:

- **Treble green** `#59D6AE` — the treble ring on every board is green. Here it means _a visit that counted_.
- **Double red** `#E85C4A` — the double ring on every board is red. Here it means _a bust_.
- **Brass** `#E3A64F` — the brass surround and the light on the board. Means _the live thing_: the active turn, the primary action, the bull.
- **Cream** `#F2EDE4` — the numerals printed on the board, and the sisal. Means _primary text_.
- **Board black** `#0C0C0E` — the sisal. Means _the surface_.

**Focus ring:** `ink` `#F2EDE4` — **14.23–17.16:1** on every surface. Deliberately **not brass**: brass-on-brass measured **1.0:1** (invisible). The ring is always cream with a 2px offset.

**Decorative hairline** `rule` `#2A2A31` measures 1.17–1.40:1. It is permitted **only** for non-meaningful separators (row rules in the score sheet, table gridlines). It must **never** be the sole indicator of a control boundary — interactive boundaries use `edge`.

**Colour-vision safety (simulated):**

- treble vs double under deuteranopia simulation: **2.83:1** separation, with a **0.28 luminance gap** (treble L 0.533, double L 0.253). Survives greyscale.
- brass vs treble under deuteranopia: **1.01:1** — effectively identical. Mitigation: they never encode the same distinction. Brass is always a **fill** (a button); treble is always **text or a rule** (a chip, a marker). Different form + a mandatory text token.
- Per the tool's own "Color Only" rule: **red text + error icon**, never a red border alone.

# PART III — DARTHUB TOKENS

## 3. Colour tokens

Tailwind v4 CSS-first `@theme` (per the `html-tailwind` stack rule: _"Define semantic design tokens with CSS-first @theme… Don't: Repeat palette utilities in components"_).

```css
/* app/globals.css */
@import "tailwindcss";

@theme {
  /* --- Surfaces: the board and its parts --- */
  --color-board: #0c0c0e; /* page ground — warm black sisal */
  --color-surface: #16161a; /* sheet, panel, card */
  --color-raised: #1e1e23; /* raised: input, key, row hover */
  --color-sunken: #08080a; /* recessed well: throw pad bed, code block */

  /* --- Rules & edges --- */
  --color-rule: #2a2a31; /* DECORATIVE hairline only (1.17-1.40:1) */
  --color-edge: #6b6b78; /* control boundary, >= 3:1 (3.16-3.81:1) */

  /* --- Ink --- */
  --color-ink: #f2ede4; /* primary text — bull cream */
  --color-ink-muted: #b9b2a6; /* secondary text */
  --color-ink-faint: #8c857a; /* tertiary text, disabled, labels */

  /* --- The accent: the lit board --- */
  --color-brass: #e3a64f; /* accent fill, active turn, bull */
  --color-brass-deep: #8a6220; /* brass border/hover on dark, not text */

  /* --- Semantic game colour --- */
  --color-treble: #59d6ae; /* a visit that counted */
  --color-double: #e85c4a; /* a bust */
}
```

**Usage rules**

- Components use `bg-surface`, `text-ink`, `border-edge` — **never** `bg-slate-800`, `text-slate-100`, `bg-blue-800`.
- Raw palette utilities (`bg-orange-500`) are banned in components. There is one accent.
- On-accent text is always `text-board`.

### 3.1 Semantic game colour — the rules

| Meaning                                                    | Token    | Also carries                       | Never                      |
| ---------------------------------------------------------- | -------- | ---------------------------------- | -------------------------- |
| A visit that counted (treble, or any legal scoring dart)   | `treble` | a `+N` value and a check icon      | used for any other purpose |
| A bust (over-scored, stranded on 1, invalid checkout)      | `double` | the word **BUST** and a cross icon | used for any other purpose |
| The live thing: active player's turn, primary action, bull | `brass`  | a label or aria state              | used for decoration        |
| Primary text                                               | `ink`    | —                                  | —                          |
| An interactive boundary                                    | `edge`   | —                                  | `rule`                     |

**Every colour is a redundant channel.** If colour is removed entirely, every state must still be readable from text, an icon, position, or shape. This is the accessibility floor, not a nicety: treble/double are only 1.4:1 apart in raw luminance.

### 3.2 Score-sheet chrome

| Token                 | Value                          | Use                                                    |
| --------------------- | ------------------------------ | ------------------------------------------------------ |
| `--sheet-row-rule`    | `1px solid var(--color-rule)`  | horizontal rule between score-sheet rows               |
| `--sheet-col-gutter`  | `var(--color-ink-faint)`       | the fixed-width numeral gutter on the left of each row |
| `--sheet-active-rail` | `2px solid var(--color-brass)` | left rail on the active player's row                   |

### 3.3 Board material tokens

**The board is an object, not a UI surface.** Its colours are paint and sisal, in their own `--board-*` family, and they never double as UI state colours. This is the **one place** the system permits material colour, gradient and texture — the surface rules above govern UI chrome, and the board is a rendered object with depth.

| Token                 | Hex       | Material                       |
| --------------------- | --------- | ------------------------------ |
| `--board-sisal-dark`  | `#141416` | painted black sisal bed        |
| `--board-sisal-light` | `#D9CFBA` | natural sisal bed              |
| `--board-red`         | `#A32B22` | red double/treble band paint   |
| `--board-green`       | `#1B6B47` | green double/treble band paint |
| `--board-bull-inner`  | `#1B6B47` | inner bull (50)                |
| `--board-bull-outer`  | `#E4DAC4` | outer bull (25)                |
| `--board-ring`        | `#0E0E10` | number ring body               |
| `--board-numeral`     | `#E8E2D4` | printed numerals               |
| `--board-wire`        | `#7A7A82` | steel wire separators          |
| `--board-steel`       | `#33333A` | outer steel surround           |

**Divergence from a physical Winmau board — deliberate, and reversible in two tokens.** A Winmau board has a **green outer bull and a red inner bull**. DartHub inverts it: **inner bull green, outer bull cream.** Rationale: in this palette red means a bust, so a red bull would collide with bust semantics beside the score sheet; cream keeps the centre from shouting. If the orchestrator prefers physical convention, it is a two-token change — but it must not be half-applied.

**How these tokens are consumed.** The `--board-*` family is **not** a Tailwind namespace, so it generates **no** utilities — `fill-board-red` and `stroke-board-wire` do not exist and cannot be made to exist. The tokens are referenced **by variable** on the SVG nodes:

```tsx
<path fill="var(--board-sisal-dark)" ... />
<path stroke="var(--board-wire)" ... />
```

They are declared in the same `@theme` block as the UI colours (they emit to `:root` like any other theme token) but they are used only inside `src/components/board/DartBoard.tsx`. **They must never appear in a component's class attribute**, because the whole point of the separate family is that board paint is not a UI state colour.

The `fill-*` / `stroke-*` utilities _do_ exist and read from `--color-*` — so `fill-board-red` would only work if the token were named `--color-board-red`, which would put board paint in the UI palette. Do not do that. Use the `var()` form above.

### 4.1 The type system

| Role        | Family           | Weight                    | Tracking  | Utility                                         | Used for                                                                                                                   |
| ----------- | ---------------- | ------------------------- | --------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **Display** | Barlow Condensed | 700                       | `-0.01em` | `font-display font-bold`                        | Mode names ("501", "Around The Clock"), sheet header, the big score in a result. All-caps permitted for short labels only. |
| **Title**   | Barlow Condensed | 600                       | `0`       | `font-display font-semibold`                    | Section headings, the active sheet title.                                                                                  |
| **Heading** | Barlow Condensed | 600                       | `0.01em`  | `font-display font-semibold`                    | Row-group labels ("PLAYERS", "LAST VISIT").                                                                                |
| **Body**    | Barlow           | 400                       | `0`       | `font-body`                                     | Descriptions, rule text on the hub, empty states, helper text.                                                             |
| **Label**   | Barlow           | 500                       | `0.02em`  | `font-label`                                    | Button labels, field labels, chips.                                                                                        |
| **Caption** | Barlow           | 500                       | `0.04em`  | `font-caption`                                  | Metadata, timestamps, axis-like labels. Uppercase + wide tracking for column heads.                                        |
| **Score**   | JetBrains Mono   | 700 (xl/lg) / 500 (md/sm) | `-0.01em` | `font-mono font-bold` / `font-mono font-medium` | **Every number that changes.** Remaining score, points per visit, marks, averages, dart counts.                            |

**The "Utility" column is the whole recipe.** `font-display` and `font-mono` set the
**family** only — they come from `@theme` and carry no weight. The weight comes from
Tailwind's own `font-bold` / `font-semibold` / `font-medium` utilities. The three roles
whose weight is fixed (`font-body`, `font-label`, `font-caption`) are single utilities that
carry family _and_ weight — see §4.4.

**Tracking** is applied with Tailwind's `tracking-*` utilities where the role calls for it
(`tracking-wide` for the caption's `0.04em`), not baked into the font utility.

### 4.2 Tabular figures — non-negotiable

Any number that changes **must** use `font-mono` (JetBrains Mono is monospaced, so figures are tabular by construction) **and** must not reflow.

```css
@utility numeric {
  font-family: var(--font-mono);
  font-variant-numeric: tabular-nums;
  font-feature-settings:
    "tnum" 1,
    "zero" 1;
}
```

Additionally, the score column has a **fixed width** so a 3-digit → 2-digit change cannot shift the layout:

```css
.score-figure {
  font-variant-numeric: tabular-nums;
  font-family: var(--font-mono);
  min-width: 3ch;
  text-align: right;
}
```

**Do not** use Barlow Condensed for a changing number — its figures are proportional.

### 4.3 Font loading

**The `next/font` variable names must NOT be the `@theme` token names.** Both would write
`--font-display` onto the same element, and one silently overwrites the other. Use
distinct names for the loaded files, and point the `@theme` tokens at them.

```tsx
// app/layout.tsx
import { Barlow, Barlow_Condensed, JetBrains_Mono } from "next/font/google";

const display = Barlow_Condensed({
  subsets: ["latin"],
  weight: ["600", "700"],
  variable: "--font-barlow-condensed",
  display: "swap",
});
const sans = Barlow({
  subsets: ["latin"],
  weight: ["400", "500", "600"],
  variable: "--font-barlow",
  display: "swap",
});
const mono = JetBrains_Mono({
  subsets: ["latin"],
  weight: ["400", "500", "700"],
  variable: "--font-jetbrains-mono",
  display: "swap",
});

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en" className={`${display.variable} ${sans.variable} ${mono.variable}`}>
      <body>{children}</body>
    </html>
  );
}
```

`next/font` self-hosts the files — no external request, no layout shift. `display: "swap"` is required.

**The variable classes go on `<html>`, not `<body>`.** The `@theme` tokens are emitted on
`:root`, and `:root` is `<html>`. A `next/font` variable declared on `<body>` would be
invisible to a `:root`-scoped token that references it, and the font would silently
fall back.

**Use `@theme inline` for the font tokens.** With a plain `@theme`, the generated utility
is `font-family: var(--font-display)` and `:root` declares
`--font-display: var(--font-barlow-condensed), …`. With `@theme inline` the utility
carries the resolved stack directly:

```css
@theme inline {
  --font-display: var(--font-barlow-condensed), "Arial Narrow", ui-sans-serif, sans-serif;
  --font-sans: var(--font-barlow), ui-sans-serif, system-ui, sans-serif;
  --font-mono: var(--font-jetbrains-mono), ui-monospace, SFMono-Regular, monospace;
}
```

`@theme inline` still emits `--font-display` to `:root`, so hand-written CSS may use
`var(--font-display)` directly.

### 4.4 The role font utilities — `font-body`, `font-label`, `font-caption`

The type system in §4.1 has **roles**, and the component specs throughout this system
and `DESIGN.md` refer to them as `font-body`, `font-label`, `font-caption`. These are
**not** generated by `--font-display` / `--font-sans` / `--font-mono` — those produce
`font-display`, `font-sans` and `font-mono` only.

Each role carries a **family _and_ a weight**, so `@theme` font tokens (which carry only
a family) cannot express them. They are declared as `@utility` blocks:

```css
@utility font-body {
  font-family: var(--font-sans);
  font-weight: 400;
}
@utility font-label {
  font-family: var(--font-sans);
  font-weight: 500;
}
@utility font-caption {
  font-family: var(--font-sans);
  font-weight: 500;
}
```

**Do not** declare an `@utility font-display` — it collides with the `@theme
--font-display` token, both rules are emitted, and the later one wins. `font-display`
and `font-mono` come from `@theme`; the three weight-bearing roles come from
`@utility`. Weight is then set with Tailwind's own `font-bold` / `font-semibold` /
`font-medium` utilities where a role needs a different weight.

4pt grid. The persisted density-8 table is retained as the base and extended.

| Token         | Value  | Named role                                                 |
| ------------- | ------ | ---------------------------------------------------------- |
| `--space-xs`  | `2px`  | hairline gap, icon inset                                   |
| `--space-sm`  | `4px`  | inline gap, chip padding-y                                 |
| `--space-md`  | `8px`  | **minimum gap between interactive targets**, tight row gap |
| `--space-lg`  | `12px` | cell padding-y, control gap                                |

### 5.1 How the spacing tokens become utilities — read this before writing a class

**This scale is declared twice, and the second declaration is not optional.**

Tailwind v4 generates utilities from a fixed set of theme namespaces. `--space-*` is a
real one, but it feeds **only** the `space-x-*` / `space-y-*` utilities. It does **not**
feed `p-*`, `m-*`, `gap-*` or `size-*` — those come from `--spacing-*`.

So the token layer declares **both**:

```css
@theme {
  /* the token names — used by hand-written CSS as var(--space-md), and by space-x-*/space-y-* */
  --space-xs: 2px;   --space-sm: 4px;   --space-md: 8px;   --space-lg: 12px;
  --space-xl: 16px;  --space-2xl: 24px; --space-3xl: 32px; --space-4xl: 48px;

  /* the utility-generating aliases — same values */
  --spacing-xs: 2px;   --spacing-sm: 4px;   --spacing-md: 8px;   --spacing-lg: 12px;
  --spacing-xl: 16px;  --spacing-2xl: 24px; --spacing-3xl: 32px; --spacing-4xl: 48px;
}
```

| Utility wanted               | Generated by                     | Example                                |
| ---------------------------- | -------------------------------- | -------------------------------------- |
| `p-md`, `px-md`, `pt-md`     | `--spacing-md`                   | `p-md` → `padding: var(--spacing-md)`  |
| `m-2xl`, `mx-auto`           | `--spacing-2xl`                  | `m-2xl` → `margin: var(--spacing-2xl)` |
| `gap-lg`                     | `--spacing-lg`                   | `gap-lg` → `gap: var(--spacing-lg)`    |
| `size-5`                     | `--spacing-5` (numeric scale)    | unchanged by the named tokens          |
| `space-x-2xl`, `space-y-3xl` | `--space-*` **or** `--spacing-*` | either namespace works                 |

**There is no bare `space-*` utility in Tailwind v4.** `space-2xl` does not exist and
cannot be made to exist — the utility is axis-specific: `space-x-2xl` or `space-y-2xl`.
Where this system previously wrote `space-2xl` / `space-3xl` / `space-md` as a class
name, it means **`space-y-*`** (vertical rhythm between stacked siblings) or **`gap-*`**
(flex/grid gap). Those are different mechanisms and are not interchangeable.

**Rule for components:** use the **utility** form (`gap-md`, `p-xl`, `space-y-2xl`).
Use the **variable** form (`var(--space-md)`) only in hand-written CSS. Never write
`var(--space-md)` inside a Tailwind class attribute.

> Verified against `tailwindcss@4.3.5` by compiling `@theme` blocks through
> `@tailwindcss/postcss` and inspecting the emitted CSS. See
> `reports/design/grounding/tw-verification.md`.

## 8. Motion tokens

```css
@theme {
  --duration-instant: 80ms; /* press feedback */
  --duration-fast: 120ms; /* hover, focus, small state change */
  --duration-base: 200ms; /* panel, sheet, expansion */
  --ease-out: cubic-bezier(0.2, 0, 0, 1); /* entering */
  --ease-in: cubic-bezier(0.4, 0, 1, 1); /* leaving */
  --ease-standard: cubic-bezier(0.4, 0, 0.2, 1);

  /* the utility-generating aliases — same values */
  --transition-duration-instant: 80ms;
  --transition-duration-fast: 120ms;
  --transition-duration-base: 200ms;
}
```

**`--duration-*` does not generate the `duration-*` utility.** Tailwind v4 resolves
durations through `--transition-duration-*`. Declaring `--duration-fast` alone produces
the custom property and **no** `duration-fast` class; declaring
`--transition-duration-fast` produces `duration-fast` → `transition-duration:
var(--transition-duration-fast)`. Both declarations are needed — the `--duration-*` names
are the token names, the `--transition-duration-*` names are what make the utilities
exist.

`--ease-*` **does** generate directly: `ease-out`, `ease-in`, `ease-standard`.

| Interaction          | Duration | Easing   |
| -------------------- | -------- | -------- |
| Button press         | 80ms     | ease-out |
| Hover / focus colour | 120ms    | ease-out |
| Sheet / panel enter  | 200ms    | ease-out |
| Panel leave          | 160ms    | ease-in  |

**Rules**

- Animate `opacity` and `transform` only. Never `width`, `height`, `top`, `left`.
- **No layout-shifting hover.** No `scale`. The tool's own anti-pattern list bans it, and the current Game Center's `hover:scale-[1.02]` violates it.
- No scroll-reveal, no parallax, no marquee, no looping animation. The persisted GSAP snippet is rejected — GSAP is not a dependency and scroll-reveal is decoration.
- A number that changes does **not** animate. It changes instantly. Animation on a score would delay the read.

### 8.1 Reduced motion

```css
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

This is a **hard requirement**, not optional. There is currently no `prefers-reduced-motion` rule anywhere in the codebase.

### 10.2 The score sheet (core component)

The product's primary object. Structure, top to bottom:

```
┌──────────────────────────────────────────────────────────┐
│ 501                          LEG 2/5      SET 1/3        │  ← sheet header
├──────────────────────────────────────────────────────────┤
│ ┃ Dave          │ 140 │  T20  T20  D16  │  ●● ○          │  ← active row (brass rail)
│   Sam          │ 132 │  S7   T19  T13  │  ● ● ○          │
└──────────────────────────────────────────────────────────┘
```

- One row per player. **Order is stable** — players do not reorder as scores change.
- The **active player** is marked by: a 2px brass left rail, `text-ink` (vs `text-ink-muted` for inactive), and a visible **"TURN"** label. Not by colour alone.
- The score figure is `--text-score-xl`, `font-mono`, `tabular-nums`, right-aligned, **fixed width** (`min-width: 3ch`).
- The score column carries a **mode-aware caption** — `REMAINING`, `HIT`, `MARKS` — in the sheet header, `font-caption` uppercase `text-ink-faint`. The number treatment is identical in every mode; the label is not.
- Each row shows the player's **last visit**: the darts thrown, each with a segment badge (`T20`, `D16`, `S7`, `BULL`).
- A bust in the last visit shows a `double`-coloured **BUST** chip with a cross icon and the word BUST — never a red border alone.
- Row separators are 1px `rule` hairlines. Row height **56px minimum** on desktop, **64px** on mobile.
- **No cards, no rounded boxes, no colour wash per player.**

#### 10.2.1 The BUST chip is computed by the UI, not by the engine

**This is the single most load-bearing fact about the score sheet, and it is invisible
from the engine's API.**

`StandardMode.applyThrow` **throws** `GameEngineStateError("Bust: …")` when a dart busts,
and `GameEngine.recordThrow` propagates it. **A bust never reaches the UI as a state.**
The engine's own README states it: _"Busts are rejected outright (`GameEngineStateError`)
and leave the match state untouched."_

Three consequences the score sheet depends on:

1. **The UI computes the bust itself.** Before submitting, the UI knows the out rule in
   force, the player's remaining score, and the dart's `{ points, segment }` — enough to
   determine that the dart busts. It must **not** infer a bust from the absence of a state
   change, and it must **not** string-match the error message: "not your turn" is also a
   `GameEngineStateError`, and a string match would report a bust for it.
2. **A bust does not consume a dart.** The engine leaves `throwsInCurrentTurn` and the
   score untouched, so the busted dart is not in the returned state and the dart counter
   does not advance. **The BUST chip is UI-local state for the current visit.**
3. **A bust does not end the turn.** The engine keeps the same `currentPlayerId`. The UI's
   turn indicator follows the engine's `currentPlayerId`, never its own notion of whose
   turn it is.

So the visit strip is assembled from **two** sources: the engine's returned state for the
counted darts, and a small UI-local record for the busted dart. Both are needed for the
green-counted / red-bust chips the design specifies.

#### 10.2.2 A miss carries no segment

`GameEngine.validateThrowInput` calls `isValidSegmentScore(segment, points)`, and that
helper returns `false` for any `points <= 0`. **A miss submitted with a segment is a
validation error, not a zero-scoring throw.**

So the miss is `{ points: 0 }` with the `segment` field **omitted** — not `segment:
"single"`, not `segment: null`. Every other throw carries a segment.

#### 10.2.3 The three non-x01 modes do not read `segment`

The x01 modes consume `segment` to decide a checkout. **Cricket, Around The Clock and
Shanghai derive everything from `points` and ignore `segment` entirely.** For those
modes the board's segment is a **UI label only** — it is shown in the visit badge
(`T20`, `D16`, `S7`) but it is not what the mode scores against.

Two consequences that are easy to get wrong:

- **Do not derive the point value from the segment.** For Around The Clock and Shanghai a
  triple and a single of the same number are different marks, and the modes distinguish
  them by `points` alone (`2 × target` vs `3 × target`). The board's `points` already
  carries that distinction, so it passes straight through.
- **In cricket the bull is not interchangeable.** `CricketMode.toSegmentHit(points)` maps
  `25` → bull for **one** mark and `50` → bull for **two** marks. A board hit on the inner
  bull is 50 points and counts as **two** marks; the outer bull is 25 points and counts as
  **one**. A view that collapses the two bulls loses a mark. The bull keys `50` and `25`
  are separate for exactly this reason — and so are the board's two bull regions.

### 10.3 The board input (core component)

A **realistic steel dartboard**, rendered from millimetre-accurate geometry, and the primary pointer path for throwing. **Full specification: `design-system/darthub/board.md`.**

- **Geometry.** 451 mm overall diameter. Band radii (mm): inner bull 0–6.35, outer bull 6.35–15.9, inner single 15.9–99, treble 99–107, outer single 107–162, double 162–170, number ring 170–225.5. 18° per segment, 20 segments clockwise from 20 at 12 o'clock. **The SVG viewBox is in millimetres** (`-225.5 -225.5 451 451`), so the drawing and the scoring read the same constants.
- **The SVG is not a circle graphic.** 80 individually authored annular-sector paths, steel wire separators, 20 radially-oriented numerals, procedural sisal and brushed-steel textures, an off-centre key light and a vignette.
- **Alternation is positional.** Odd position → black bed, red bands; even position → light bed, green bands.
- **Every scoring throw carries a segment.** The board's `resolveBoardHit` and the pad's segment-labelled keys both produce `{ points, segment }`. The one exception is a **miss**, which is `{ points: 0 }` with the segment omitted — see §10.2.2.
- **The armed segment** (`1× / 2× / 3×`) is shared state between the board and the pad, and is **outlined in brass on the board itself**.
- **The number ring is the sector selector.** Clicking a numeral scores the armed band of that sector. The ring is not scorable on a real board; here it is the board's largest target.
- **Hit feedback:** a dart is left at the resolved point for the whole visit, cleared when the turn ends.
- **Target size:** the painted beds are **below** the 24 px AA minimum and **cannot** be raised — the treble band is 8 mm of a 451 mm board. This is a documented deviation with a complete conformant alternative (the armed-segment + numeral route, the pad, and the board's roving-tabindex grid). See `board.md` §7 and `DESIGN.md` §8.3.2. **Do not silently resize the bands to hit a target-size number — that would misrepresent the sport.**
- **Below 768 px the board is a read-only preview** ("LAST DART"), not an input. The pad is the input.
- `prefers-reduced-motion` removes the hit animation; the dart marker and the visit log still carry the state.

### 10.5 Empty & loading states

- **Never** show `--`, `0`, or a placeholder number for data that does not exist. The current dashboard's four `--` tiles are the anti-pattern.

## 12. Implementation rules for this codebase

1. **`@theme` in `app/globals.css` is the only source of colour, spacing, radius and type.** Components reference `bg-surface`, `text-ink`, `rounded-sm` — never a palette utility.
2. **Complete class tokens only.** Tailwind cannot see interpolated class names. Write `const SEGMENT_CLASS = { triple: "bg-treble", double: "bg-double" }` — never `` `bg-${segment}-500` `` (the `html-tailwind` stack rule, Severity High).
3. **Server Components by default.** Only the interactive leaves (`"use client"`). The `nextjs` stack rule is Severity High: _"Don't: Add 'use client' unnecessarily"_ and _"Don't: Mark page as Client Component."_ Today all five match pages are client components; the static parts (sheet header, rule text) must move to server components.
4. **Use `cva`** for variant styling rather than inline conditional classes (the `shadcn` stack rule).
5. **All five match views must use the same match-view shell.** Cricket, Around The Clock and Shanghai currently have private UIs and must migrate.
6. **The segment must be sent.** `ThrowInput` already accepts `segment` and the engine validates it. Without it, Double Out cannot be won.
7. **One board-geometry resolver, no third implementation.** `src/board/boardGeometry.ts` is pure TypeScript, in millimetres, origin at the board centre, **x right / y up** — the same frame `CameraDTO` already uses. The UI click path and the future `HitDetector` both call `resolveBoardHit`. Do not re-implement the ring or wedge maths anywhere else.
8. **`ThrowSegment` is not declared twice.** `src/game-engine/types.ts` re-exports `BoardSegment` from the board module.
9. **`CameraDTO` carries the segment.** A score alone is ambiguous about its band (24 points is D12 or T8), so a camera-only Double Out would be unwinnable without it.
